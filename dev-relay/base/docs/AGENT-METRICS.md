## Overview

This document provides a practical metrics framework to measure AI agent effectiveness across four key dimensions:

1. **PR-level impact** — How agent usage influences review quality and delivery speed
2. **Review interaction patterns** — How review comments, friction, and reviewer involvement unfold during code review
3. **Development phase tracking** — How many iterations, findings, and fix cycles occur by agent and phase
4. **Model comparison** — How accurately and efficiently different AI models perform on the same work

## How To Use This Document

Use this file alongside [Agent Guide](AGENT-GUIDE.md) as your primary reference for tracking outcomes.

The current pipeline writes an operational activity log, but it does not write automated metrics telemetry or update metrics files. Record metrics manually unless and until the proposed instrumentation in this document is implemented.

### Recommended workflow

1. **Run the end-to-end story workflow from [Agent Guide](AGENT-GUIDE.md)**

    - Select **Deva** in the Chat agent/mode picker, then enter `work on <JIRA-KEY>`.
    - Proceed through every checkpoint in registry order, including both architecture gates, intake and refinement, branch setup, implementation, shared QA/testing C4, acceptance, publication, regression, review extraction, human review, any reactive re-extraction, and archival.

2. **Record metrics when their evidence becomes final**

    - After initial extraction: record delivery-slice size, mode-aware branch lineage, and provenance inputs as provisional.
    - After the applicable human-review, re-extraction, and stacked-integration path completes: finalize extraction metrics from the accepted delivery identities and lineage.
    - After QA/testing: finding categories, first-pass failures, overall/business-logic coverage, and mock accuracy.
    - After PR merge: review rounds, first-review turnaround, and cycle time.
    - After story closure: acceptance criteria marked as `Met`, `Partially Met`, `Not Met`, or `Deviated` and story-level aggregates.

3. **Review weekly and sprint trends**

    - Compare agent-assisted PR results with baseline or manual periods.
    - Monitor reviewer effort and convergence speed.
    - Track recurring review-comment categories to guide prompt and skill improvements.

4. **Use the scorecard to refine model and agent settings**

    - Apply the formulas in this document to compare quality, speed, and cost.
    - Change model or strategy only when quality stays at or above target thresholds.

### Minimum reporting cadence

- **Per PR:** Add the `ai-assisted` label and capture Tier 1 plus key Tier 2 metrics.
- **Weekly:** Publish a team-level digest that highlights trends and outliers without persisting employee identifiers in repository artifacts.
- **Per sprint:** Review improvement actions and confirm adherence to target thresholds.

## 1. PR-Level Metrics

### Standardized KPI Definitions (Required)

Use these definitions across all teams for consistency:

| KPI | Definition | Notes |
| ----- | ------------ | ------- |
| **Delivery-slice metrics** | Per review delivery capture `delivery_id`, `delivery_mode`, `branch_name`, `parent_branch`, `prod_lines_added`, `test_lines_added`, `tests_passing`, and `ac_covered[]` | Direct mode uses one `delivery_id` equal to `feature/<user>/<PARENT-JIRA>`; stacked mode uses one row per parent-story ordinal `PR<N>` branch |
| **% AI Test Creation** | `(AI-authored new test cases / Total new test cases) x 100` | Use test cases, not lines of code |
| **AI-assisted test %** | `(AI-assisted new test cases / Total new test cases) x 100` | Track separately from fully AI-authored |
| **Human-authored test %** | `(Human-authored new test cases / Total new test cases) x 100` | Complements AI metrics |

Classification rule for test origins:

- `AI-authored`: generated by tester agent with no substantive human rewrite.
- `AI-assisted`: generated by AI and materially edited by a human before merge.
- `Human-authored`: written by a human without AI-generated baseline.

Historical backfill rule:

- If a period lacks explicit test-origin markers, report with `data_confidence: estimated`.
- Keep exact and estimated values separate in dashboards.

### Tier 1 — Direct PR Metrics

| Metric | What It Measures | How to Collect |
| -------- | ----------------- | ---------------- |
| **PR cycle time** | Time from PR opened → merged | Project-native SCM API (for example, GitHub or Bitbucket; compare before/after agent adoption) |
| **First-review turnaround** | Time from PR opened → first review comment | Project-native SCM API (for example, GitHub or Bitbucket) |
| **Review rounds** | Number of review iterations before approval | Count "changes requested" events per PR |
| **PR size (non-test lines changed)** | (target: ≤300 non-test lines) | Project-native SCM diff stats, summing additions plus deletions after excluding repository-defined test paths; record total test-line churn separately |
| **Test coverage delta** | Coverage change introduced by the PR | CI coverage reports (before/after diff) |
| **Defect escape rate** | Bugs found in QA/prod from agent-assisted PRs vs manual | Tag PRs with `ai-assisted` label, correlate with bug tickets |

### Tier 2 — Agent-Specific Metrics

| Metric | What It Measures | How to Collect |
| -------- | ----------------- | ---------------- |
| **Agent invocations per PR** | How much the engineer leans on agents | Log calls by agent identity and invocation event (for example, Deva, QA, and Tester) |
| **Agent acceptance rate** | % of agent suggestions kept vs. reverted | Compare a retained agent candidate diff or reviewed provenance record against final merged code; unavailable without that evidence |
| **QA escaped-defect rate** | Valid defects first reported by reviewers or later QA after the QA-agent pass | Adjudicate each later defect against the QA snapshot; `escaped valid defects / all known valid defects`. Use the golden-set precision/recall method below when a seeded known-defect set exists |
| **Test origin distribution** | AI-authored, AI-assisted, and human-authored new test cases | Classify discovered new test cases using review evidence; file tags identify an AI-generated baseline but do not attribute overlapping production-line coverage |
| **Rework after agent** | Lines changed after agent generated code (in same PR) | Compare retained candidate-line provenance with later PR revisions; Git blame alone cannot identify AI-origin lines |

For either provenance-dependent metric, record `data_confidence: exact` only when a retained candidate diff or reviewed line-provenance record supports the calculation. Use `estimated` when documented review evidence supports a bounded manual estimate. When neither exists, report `unavailable`; do not infer AI authorship from Git blame, commit authorship, or the test-file marker.

### Tier 3 — Team Productivity

| Metric | What It Measures | How to Collect |
| -------- | ----------------- | ---------------- |
| **Stories completed per sprint** | Team throughput | Jira sprint reports, aggregated before publication |
| **Time-to-first-commit** | How quickly work starts after story pickup | Jira transition timestamp → first commit timestamp, reported as a team distribution |
| **Concurrent work** | How many PRs/stories the team has in progress | Aggregate WIP count from Jira and the project-native SCM |
| **First-round approval rate** | How often team PRs pass review on the first round | `approved_first_round / total_PRs` |

## 2. Review Interaction Patterns

### Review Complexity Scoring

Break down each PR's review lifecycle into granular events:

| Event Type | What to Track | Source |
| ------------ | --------------- | -------- |
| **Review comments** | Each individual comment (inline + general) | Project-native SCM review API (for example, GitHub PR reviews or Bitbucket PR comments) |
| **Change requests** | Formal change-request outcomes | Project-native SCM review states or unresolved review tasks |
| **Approvals** | Formal approvals | Project-native SCM approval states |
| **Unique reviewers** | Distinct engineers who commented/reviewed | Deduplicate review authors |
| **Comment threads** | Back-and-forth conversations (reply chains) | Thread depth per comment |

### Review Friction Score

```text
friction = (change_requests × 3) + (comment_threads × 1) + (reply_depth_avg × 0.5)
```

Lower = cleaner PR. Compare agent-assisted vs. manual PRs at team or sufficiently large cohort level.

### Single vs. Multi-Reviewer Breakdown

| Scenario | What It Tells You |
| ---------- | ------------------- |
| 1 reviewer, 0 change requests | Clean PR — agent did well |
| 1 reviewer, 1+ change requests | Agent missed something the reviewer caught |
| 2+ reviewers, each with comments | Complex PR or agent output needs multiple perspectives to validate |
| 2+ reviewers, only 1 has comments | Second reviewer rubber-stamped — not a real signal |

**Derived metrics:**

```text
single_reviewer_approval_rate = PRs approved by 1 reviewer with 0 changes / total PRs
multi_input_rate = PRs where 2+ reviewers requested changes / total PRs
```

### Comment Category Tagging

Categorize each review comment to identify what agents miss most often:

| Category | Example | Agent Implication |
| ---------- | --------- | ------------------- |
| **Logic bug** | "This will NPE if list is empty" | Agent missed an edge case |
| **Style/convention** | "We use snake_case here" | Agent doesn't know project conventions |
| **Architecture** | "This should be in the service layer" | Agent scoped the task wrong |
| **Missing requirement** | "AC says we also need to handle X" | Agent prompt was incomplete |
| **Nitpick** | "Add a blank line here" | Noise — not meaningful |
| **Security** | "Don't log the token" | Agent introduced a vulnerability |
| **Test gap** | "What about the error case?" | Tester agent missed coverage |

Keyword matching on comments (`"test"`, `"security"`, `"naming"`, `"missing"`) can provide a baseline for automated categorization; measure and report its accuracy against a reviewed local sample before relying on it.

### Reviewer Effort Score

```text
reviewer_effort = total_comments + (change_request_rounds × 5) + (unique_files_commented × 2)
```

If agents are working well, reviewer effort should drop over time.

### Convergence Speed

```text
convergence = time_from_first_change_request → final_approval
```

Measures how quickly the engineer (with agent help) addresses review feedback.

## 3. Development Phase Tracking

### Proposed Instrumentation Approach

For future automation, **do not create a separate tracking agent.** Embed telemetry into existing agents via a shared logging utility.

```text
deva           ──→  logs: session_start, story_key, delivery_mode, review_slices_prepared (Step 8)
  implementation-partner  ──→  logs: files_changed, lines_written, iteration_number
  qa             ──→  logs: findings_count, severity_breakdown
  tester         ──→  logs: tests_generated, coverage_delta
  acceptance-checker  ──→  logs: ac_met, ac_partial, ac_not_met, ac_deviated
```

Under this proposed design, each agent would return structured metric events to Deva. Deva would pass those events to `pipeline-session`, the sole session and activity writer, which would append them to the story's durable metrics log. This behavior is not currently implemented.

### Event Schema

```json
{
  "timestamp": "2026-05-08T14:30:00Z",
  "agent": "qa",
  "story": "PROJ-1234",
  "delivery_id": "PR1",
  "event": "qa_review_complete",
  "data": {
    "findings": 3,
    "categories": {"bug": 1, "security": 0, "style": 1, "resource_leak": 1},
    "iteration": 1
  }
}
```

**Proposed storage:** Jira-keyed JSONL at `.github/artifacts/sessions/<JIRA-KEY>/<JIRA-KEY>-YYYYMMDD.jsonl`. The file persists across chat sessions and follows `pipeline.archive_retention_days`; only `pipeline-session` writes it. Agents receive only the metric context needed for their stage and return new events through Deva. Durable events and committed rollups must not contain employee names, SIDs, email addresses, or other engineer identifiers; any identity-based analysis belongs in an access-controlled analytics system and is joined transiently outside repository artifacts.

### Metrics Per Development Session

| Phase | Metric | What It Reveals |
| ------ | -------- | ----------------- |
| **Dev Assistant (decomposition)** | Subbranch count per story (Step 8) | Are stories being sliced into reviewable PRs? |
| **Implementation Partner** | Iterations per approved work unit | How many times the agent rewrote code before acceptance |
| **Implementation Partner** | Error-fix cycles | Code → error → fix → error → fix (count these) |
| **Implementation Partner** | Files touched | Blast radius of the change |
| **QA** | Findings per run | Are findings dropping across iterations? (code is converging) |
| **QA** | Finding categories | Logic bugs vs. style vs. security — which type recurs? |
| **Tester** | Tests that fail on first run | Agent-generated tests that don't pass immediately |
| **Tester** | Mock accuracy | Tests fail because mocks are wrong vs. logic is wrong |
| **acceptance-checker** | AC alignment score | After dev is "done", how many AC are actually met? |

### Example Iteration Log

```text
Approved work unit: PROJ-1234 implementation
  Iteration 1: implementation-partner writes code
    → QA finds 3 issues (unused import, missing retry, resource leak)
    → implementation-partner fixes
  Iteration 2: implementation-partner applies fixes
    → QA finds 0 issues ✓
    → tester generates 3 tests, 2 pass, 1 fails
    → implementation-partner fixes test
  Iteration 3: all tests pass
    → acceptance-checker: 4/4 AC met ✓

  Total iterations: 3
  QA findings absorbed: 3
  Test fix cycles: 1
```

## 4. Model Comparison Framework

### Building a Golden Dataset

Use completed stories as test cases. Every story worked on with agents is a benchmark:

| Input | Expected Output | Source |
| ------- | ----------------- | -------- |
| Jira story description | Direct feature delivery or parent-story ordinal review-slice breakdown | What Deva actually produced at Step 8 |
| Approved work-unit prompt | The merged code | Implementation Partner output + engineer fixes |
| Code snapshot pre-QA | Known findings list | What QA agent found |
| Implementation code | Test functions with correct mocks | What tester agent produced |
| Final code vs AC | AC verdict | What acceptance-checker validated |

**Target: 10-20 golden stories** from real completed work.

### Scoring Per Agent Role

| Agent | Evaluation Method | Scoring |
| ------- | ----------------- | --------- |
| **deva (decomposition step)** | Compare subbranch decomposition against golden breakdown | Precision/recall on subbranches |
| **implementation-partner** | Diff generated code against merged code | `lines_kept_as_is / total_lines_generated` |
| **qa** | Compare findings against known issues list | True positives, false positives, false negatives |
| **tester** | Run generated tests — do they pass? Coverage? | Pass rate + coverage delta + mock correctness |
| **acceptance-checker** | Compare AC verdict against human review | Agreement rate on Met/Partially Met/Not Met/Deviated |

### Key Formulas

#### Functional Accuracy (implementation-partner)

```text
code_accuracy = lines_kept_unchanged / lines_generated
```

#### Precision & Recall (QA and acceptance-checker agents)

```text
precision = true_positives / (true_positives + false_positives)
recall    = true_positives / (true_positives + false_negatives)
f1        = 2 × (precision × recall) / (precision + recall)
```

#### First-Pass Success Rate

```text
first_pass = tasks_with_zero_corrections / total_tasks
```

#### Token Efficiency

```text
token_efficiency = accepted_output_tokens / total_output_tokens
```

For every ratio above, when its denominator is zero, record the metric as `n/a` and exclude it from averages that require that metric. Record `f1` as `n/a` when precision or recall is `n/a`, or when `precision + recall` is zero.

`accepted_output_tokens` is measured only in a controlled model-comparison run: tokenize the exact generated candidate and the reviewer-approved retained spans with the same tokenizer, then count candidate tokens that survive in those retained spans. Exclude system prompts, tool payloads, and user input from both values. Do not report this metric when retained-span evidence or tokenizer identity is unavailable.

### Model Comparison Scorecard

```text
                      Model A (Baseline)   Model B (New)
                      ------------------   -------------
Code accuracy         90%                  58%
QA precision          1.00                 0.60
QA recall             1.00                 1.00
Test first-pass rate  100%                 50%
AC agreement          100%                 75%
Avg iterations        2.1                  3.8
Token efficiency      87%                  62%
Avg latency/task      45s                  22s
Cost per story        $0.85                $0.40

Winner by quality:    Model A ✓
Winner by speed:                           Model B ✓
Winner by cost:                            Model B ✓
```

### Evaluation Approaches

| Approach | How Works | Pros | Cons |
| ---------- | ------------- | ------ | ------ |
| **Offline eval** | Run golden inputs through each model via API, compare outputs | No production risk, fully repeatable | Doesn't capture real-world variability |
| **A/B in production** | Randomly assign stories to Model A or B for 2 weeks | Real-world signal | Noisy — harder stories may land on weaker model |
| **Shadow mode** | Model A is primary, Model B runs in background on same inputs | No risk, real-world inputs | Requires extra compute, no interactive correction signal |

### The Break-Even Question

```text
If Model B saves $X per story but adds Y iterations × Z minutes of engineer time:

  worth_switching = $X > (Y × Z / 60 × engineer_hourly_rate)
```

### What "Good" Looks Like

| Metric | Target |
| -------- | -------- |
| Code accuracy | ≥ 80% |
| QA precision | ≥ 0.70 |
| QA recall | ≥ 0.90 |
| Test first-pass rate | ≥ 85% |
| AC agreement | ≥ 85% |
| Avg iterations/approved work unit | ≤ 2.5 |
| Review rounds | ≤ 1.5 avg |
| PR cycle time reduction | ≥ 30% vs. baseline |
| Defect escape rate | No increase vs. baseline |
| Rework rate | ≤ 20% |

## Getting Started

1. **Tag agent-assisted PRs** — Add the `ai-assisted` label to every PR where agents were used.
2. **Run the checklist consistently** — Use [Agent Metrics Checklist](AGENT-METRICS-CHECKLIST.md) for per-PR, weekly, and sprint data capture.
3. **Establish a baseline first** — Collect 2-3 sprints of historical PR data from before agent adoption.
4. **Plan future instrumentation** — When automation is approved, add structured logging to existing agent entry points.
5. **Build a golden-story benchmark set** — Save 10-20 completed story inputs and outputs for comparison.
6. **Publish a weekly digest manually** — Aggregate manually recorded outcomes until automated session summaries exist.
7. **Run a sprint retrospective on metrics** — Review trends and identify which agent needs tuning.
